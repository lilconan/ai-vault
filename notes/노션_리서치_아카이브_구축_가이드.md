# 클로드코드로 리서치 문서를 노션에 자동 정리하는 시스템 — 설계 + 도구 리서치

> **리서치 날짜**: 2026-09-12
> **부패속도**: 빠름 (스타 수·설치 수·플러그인 버전이 근거라 3개월이면 재확인 필요)
> **분류**: 도구·워크플로
> **용도**: 정리 안 된 리서치 문서를 클로드코드에 던지면 노션 DB에 일정한 형식으로 쌓이게 만드는 구조 + 그에 쓸 공개 스킬 목록

---

## TL;DR

- 노션 DB를 **2개**로 쪼갠다. `📚 리서치 아카이브`(문서 1개 = 1행)와 `🧰 도구·레시피`(도구 1개 = 1행). 문서 하나에 도구가 여러 개 들어있는 경우가 많은데, 나중에 찾아 쓰는 단위는 문서가 아니라 도구다.
- "언제쩍 자료냐"는 **리서치 날짜 + 부패속도 + 신선도 수식** 세 속성으로 푼다. 노션 기본 `생성 일시`는 쓸모없다.
- 본문은 **5블록 고정**. 마지막 블록에 원문 전체를 토글로 접어 넣어서, 요약본은 짧게 유지하면서 원문은 안 잃는다.
- 도구는 **노션 공식 플러그인**(`makenotion/claude-code-notion-plugin`)을 깔면 MCP + Knowledge Capture·Research Documentation 스킬이 한 번에 들어온다.
- 다만 **내 DB 스키마를 강제하는 슬래시 커맨드는 직접 만들어야 한다.** 스키마는 개인 것이라 공개 스킬이 대신 못 해준다. 부록 A에 완성본이 있다.

---

## 1. 왜 이 구조인가

### 1-1. 문서가 아니라 도구가 알맹이다

리서치 문서 하나에 설치해서 쓸 수 있는 도구가 5~6개 들어있는 경우가 흔하다. 이걸 페이지 하나에 줄글로 뭉쳐놓으면 3개월 뒤 "내가 깐 게 뭐였더라" 찾을 때 페이지를 열어 처음부터 읽어야 한다. 도구를 별도 행으로 쪼개면 `상태 = 설치함` 필터 하나로 현재 스택이 한눈에 보인다.

앞으로 도구 리서치가 아닌 문서(시장 조사, 개념 정리 등)가 들어오면 도구 DB는 비워두면 된다. 구조는 안 깨진다.

### 1-2. 날짜 하나로는 부족하다

`생성 일시`는 노션에 넣은 날이지 리서치한 날이 아니다. 게다가 같은 문서 안에서도 부패 속도가 다르다. GitHub 스타 수는 3개월이면 썩고, 언어학 이론이나 고전 텍스트는 10년 뒤에도 유효하다. 그래서 **날짜 + 부패속도**를 따로 받고 수식으로 합쳐야 한다.

### 1-3. 요약하면 안 되는 게 있다

설치 명령어를 AI가 "요약"하면 그냥 깨진다. 버전 번호, 수치, URL도 마찬가지다. verbatim 보존 규칙을 못 박지 않으면 이게 제일 흔한 실패 지점이 된다.

## 2. DB 설계

```
📚 리서치 아카이브   (문서 1개 = 1행, 원문 보관)
        ↕ relation
🧰 도구·레시피       (도구 1개 = 1행, 실제로 쓰는 것)
```

### 2-1. 📚 리서치 아카이브

| 속성 | 타입 | 용도 |
|---|---|---|
| 제목 | 제목 | `[분야] 핵심 내용` 형식. 40자 이내 |
| 한줄요약 | 텍스트 | 30자 이내. 목록에서 열지 않고 파악 |
| 분류 | 선택 | 도구·워크플로 / 개념·이론 / 시장·트렌드 / 레퍼런스 |
| 태그 | 다중선택 | 한국어, 클로드코드, 글쓰기 … |
| **리서치 날짜** | 날짜 | ★ 원문에서 추출. 생성일시 아님 |
| **부패속도** | 선택 | 빠름 / 보통 / 안썩음 |
| **신선도** | 수식 | ★ 아래 수식 |
| 상태 | 상태 | 미확인 → 읽음 → 적용함 / 보류 / 폐기 |
| 출처 | URL | 원본 링크. 없으면 비워둔다 |
| 관련 도구 | 관계 | → 도구 DB |

**신선도 수식** (노션에 그대로 붙여넣기)

```
if(empty(prop("리서치 날짜")), "❓ 날짜없음",
  if(dateBetween(now(), prop("리서치 날짜"), "days") > if(prop("부패속도") == "빠름", 90, if(prop("부패속도") == "보통", 365, 3650)),
    "🔴 재확인 필요",
    if(dateBetween(now(), prop("리서치 날짜"), "days") > if(prop("부패속도") == "빠름", 45, if(prop("부패속도") == "보통", 180, 1825)),
      "🟡 슬슬 오래됨", "🟢 신선")))
```

🔴 필터 뷰를 하나 만들어두면 그게 곧 재확인 목록이 된다.

**부패속도 판단 기준**

| 값 | 기준 | 임계값 |
|---|---|---|
| 빠름 | GitHub 스타 수, 버전 번호, 가격, 모델 성능 비교, "현재 최신" 류 | 45일 / 90일 |
| 보통 | 도구 사용법, 워크플로, 설정 방법 | 180일 / 365일 |
| 안썩음 | 언어학·이론·규범, 논문, 고전 텍스트 | 5년 / 10년 |

한 문서에 여러 개가 섞여 있으면 제일 빠른 쪽으로 잡는다.

### 2-2. 🧰 도구·레시피

| 속성 | 타입 | 용도 |
|---|---|---|
| 이름 | 제목 | 레포명 그대로 (`snflkd/fluent-korean`) |
| 뭐하는 건지 | 텍스트 | 한 줄 |
| **설치 명령어** | 텍스트 | ★ 복붙용. 원문에서 글자 그대로 |
| 종류 | 선택 | 플러그인 / 스킬 / output-style / CLAUDE.md 규칙 / MCP |
| 상태 | 상태 | 후보 / 설치함 / 뺐음 |
| 링크 | URL | 레포 주소 |
| 마지막 확인 | 날짜 | 스타 수·버전 확인한 날 |
| 출처 문서 | 관계 | ← 리서치 DB |

### 2-3. 페이지 본문 5블록

```
## 1. 용도       — 왜 필요한가 (2~3줄)
## 2. 바로 실행   — 복붙 가능한 코드블록만
## 3. 선택 기준   — 여러 개 중 뭘 언제 쓰나 (선택지 하나면 생략)
## 4. 함정       — 한계·주의·오탐 사례
## 5. ▶ 원문 전체 — 토글 블록. 한 글자도 안 빼고
```

5번이 핵심이다. 검색은 되는데 눈에는 안 띈다. "필요한 내용만 보기"와 "나중에 원문 확인"을 동시에 만족하는 유일한 방법이다.

## 3. 쓸 만한 공개 도구 (2026-09 기준)

### 3-1. 노션 공식 플러그인 — 제일 먼저 깔 것

`makenotion/claude-code-notion-plugin` · 스타 456 · Notion Labs 공식

MCP 서버 + Notion Cookbook 스킬 4종 + 슬래시 커맨드를 한 번에 묶어서 설치한다. 이걸 깔면 `claude mcp add`를 따로 안 해도 된다.

```
/plugin marketplace add makenotion/claude-code-notion-plugin
/plugin install notion-workspace-plugin@notion-plugin-marketplace
```

설치 후 **클로드코드 재시작** 필요. 인증은 OAuth.

포함된 스킬 4종:

| 스킬 | 하는 일 |
|---|---|
| **Knowledge Capture** | 대화·문서에서 개념·결정·절차를 뽑고, 노션을 검색해 위치를 찾고, 페이지를 만들고, 허브에서 링크를 건다. 기존 페이지가 있으면 갱신한다 |
| **Research Documentation** | 노션을 검색해 여러 페이지를 종합하고 출처가 달린 리서치 문서를 다시 써넣는다 |
| Meeting Intelligence | 회의 준비용 컨텍스트·아젠다 생성 |
| Spec to Implementation | 스펙을 작업 계획으로 변환 |

앞의 두 개가 이 시스템에 직접 쓰인다.

주요 슬래시 커맨드: `/Notion:search`, `/Notion:create-page`, `/Notion:database-query`, `/Notion:create-database-row`, `/Notion:find`

**OpenAI 포팅 버전**도 있고 설치 수는 이쪽이 더 많다(1.5k).

```
npx -y skills add openai/skills --skill notion-knowledge-capture --agent claude-code
```

### 3-2. treylom/knowledge-manager — 한국어 종합형

스타 223 · MIT · 문서 전체 한국어

웹페이지·PDF·YouTube 자막·카카오톡 대화를 받아 Zettelkasten 원칙으로 분석하고 Obsidian이나 노션에 저장한다.

```

/plugin install km@knowledge-manager
/km:setup
```

**주의**: 셋업 위저드가 Obsidian vault 경로를 받아 스킬 파일의 플레이스홀더(`{{VAULT_PATH}}` 등)를 치환하는 구조라 Obsidian 중심 설계다. 웹 추출에는 Playwright MCP가 별도로 필요하다. 노션만 쓸 거면 설치 비용 대비 이득이 적다. 유튜브·PDF·카톡까지 던지게 되면 그때 다시 볼 것.

### 3-3. AgriciDaniel/claude-obsidian — Obsidian 쪽 최강자

스타 14.8k · MIT · Generic·LYT·PARA·Zettelkasten 파일링 규칙 선택 가능. 노션 쓸 거면 볼 필요 없다.

### 3-4. 없는 것

앤트로픽 공식 스킬 저장소(`anthropics/skills`)에는 지식 정리·노션 파일링 스킬이 없다. 공식은 문서 생성(pdf·docx·xlsx·pptx), 디자인·브랜딩, 엔지니어링 워크플로 중심이고 지식관리는 전부 커뮤니티 제작이다.

더 근본적으로, **"정리 안 된 문서 던지면 알아서 내 DB 스키마에 맞춰 넣어주는" 스킬은 원리상 존재할 수 없다.** 스키마가 개인 것이기 때문이다. Knowledge Capture도 자기 reference 폴더의 일반 DB 템플릿을 쓰지, `부패속도`·`신선도` 같은 내 속성은 모른다.

## 4. 조합 방식

| 층 | 무엇이 | 역할 |
|---|---|---|
| 플러그인 | 노션 공식 | MCP 연결 + 검색·페이지 생성·DB 쓰기 도구 |
| 스킬 | Knowledge Capture | 구조화·링크·중복 갱신 일반 노하우 |
| 커맨드 | `/노션정리` (부록 A) | **내 DB 스키마와 5블록 템플릿 강제** |

### 실전 함정: 스킬은 직접 호출이 약하다

슬래시 커맨드와 서브에이전트는 명시적으로 실행할 수 있지만, 스킬은 Claude가 알아서 써주기를 기대해야 한다. 플러그인의 `skills/*/SKILL.md`가 Skill 도구로는 동작하는데 `/플러그인명:스킬명` 형태의 슬래시 호출로는 안 잡히는 이슈도 보고돼 있다.

그래서 Knowledge Capture를 깔아놔도 "알아서 발동하겠지"라고 믿으면 안 된다. 커맨드 본문에 아래 한 줄을 넣어라. 커맨드가 트리거가 되고 스킬이 내용을 채운다.

```markdown
## 참고
Notion Knowledge Capture 스킬의 중복 확인·링크 연결 절차를 따르되,
DB 속성과 본문 5블록 구조는 이 문서의 규칙을 우선한다.
```

**우선순위 명시가 핵심이다.** 안 그러면 스킬의 기본 템플릿이 내 스키마를 덮어쓴다.

## 5. 설치 순서

1. 노션 공식 플러그인 설치 → 클로드코드 재시작 → OAuth 인증
2. 노션에서 DB 2개를 **손으로** 만든다 (2절 스키마)
3. `/노션정리` 커맨드 파일을 `~/.claude/commands/`에 넣고 0번 항목에 DB ID를 박는다
4. 리서치 문서 하나로 테스트하고 결과를 검수한다

### DB는 왜 손으로 만드나

클로드코드에 시키면 속성 이름이 미묘하게 달라지고, 수식·관계·상태 타입은 MCP로 만들 때 자주 깨진다. 한 번 10분 투자해서 직접 만들고 DB URL을 커맨드에 박아넣는 게 낫다. 그 뒤로는 손 볼 일이 없다.

### 운영 주의사항

- **노션 MCP는 컨텍스트를 꽤 먹는다.** 가끔 `/context`로 확인하고, 정리 작업은 `/clear` 후 새 세션에서 돌리는 게 안전하다.
- **처음 두세 번은 결과를 검수해라.** 특히 리서치 날짜 추출. 날짜가 안 적힌 문서가 섞이면 오늘 날짜로 퉁쳐버린다. 커맨드 보고 단계의 `⚠️` 줄을 반드시 확인할 것.
- **중복 확인을 생략하면 안 된다.** 계속 쌓아가는 DB에서는 중복이 제일 큰 적이다.

## 부록 A. `/노션정리` 슬래시 커맨드 전문

`~/.claude/commands/노션정리.md`에 저장. 프로젝트 하나에서만 쓸 거면 `.claude/commands/`.

````markdown
---
description: 리서치 문서를 읽어서 노션 아카이브 DB + 도구 DB에 정리해서 넣는다
argument-hint: [파일경로 또는 붙여넣은 내용]
allowed-tools: Read, Glob, Grep
---

# 리서치 문서 → 노션 정리

대상: $ARGUMENTS

아래 순서대로 진행한다. 중간에 임의로 단계를 건너뛰지 않는다.

## 0. 설정값

```
리서치 아카이브 DB: <여기에 노션 DB URL 또는 ID 넣기>
도구·레시피 DB:    <여기에 노션 DB URL 또는 ID 넣기>
```

DB ID가 비어 있으면 작업을 멈추고 사용자에게 물어본다. 임의로 새 DB를 만들지 않는다.

## 1. 읽기

대상 파일을 끝까지 읽는다. 일부만 읽고 판단하지 않는다.
파일이 아니라 붙여넣은 텍스트면 그대로 쓴다.

## 2. 중복 확인 (건너뛰지 말 것)

리서치 아카이브 DB에서 비슷한 제목·주제의 페이지를 먼저 검색한다.

- 있으면 → 새로 만들지 말고 기존 페이지를 갱신한다. 리서치 날짜를 새 날짜로 바꾸고, 달라진 부분만 수정하고, 본문 맨 아래 `## 변경 이력`에 한 줄 남긴다.
- 없으면 → 3번으로 간다.

계속 쌓아가는 DB라서 중복이 제일 큰 적이다. 이 단계를 절대 생략하지 않는다.

## 3. 속성 채우기

### 리서치 아카이브 DB

| 속성 | 채우는 법 |
|---|---|
| 제목 | `[분야] 핵심 내용` 형식. 40자 이내 |
| 한줄요약 | 30자 이내. 문서를 안 열고도 뭔지 알게 |
| 분류 | 도구·워크플로 / 개념·이론 / 시장·트렌드 / 레퍼런스 중 하나 |
| 태그 | 2~4개. 기존 DB에 이미 있는 태그를 우선 재사용한다 |
| 리서치 날짜 | 문서 본문에서 찾는다. 제목의 연도, "리서치 시점 기준", 언급된 최신 커밋·릴리스 날짜 등. 아무 데도 없을 때만 오늘 날짜를 쓰고 한줄요약 옆에 `(날짜 추정)` 표시 |
| 부패속도 | 빠름 / 보통 / 안썩음 |
| 상태 | `미확인` |
| 출처 | 원본 URL. 없으면 비워둔다. 절대 지어내지 않는다 |

부패속도 판단 기준
- `빠름` — 근거가 GitHub 스타 수, 버전 번호, 가격, 모델 성능 비교, "현재 최신" 류
- `보통` — 도구 사용법, 워크플로, 설정 방법
- `안썩음` — 언어학·이론·규범, 논문, 고전 텍스트

한 문서에 여러 개가 섞여 있으면 제일 빠른 쪽으로 잡는다.

### 도구·레시피 DB

문서에 "설치해서 쓰는 것"이 나오면 하나씩 별도 행으로 만든다. 여러 개를 한 행에 몰아넣지 않는다.

- 이름: 레포명 그대로
- 뭐하는 건지: 한 줄
- 설치 명령어: 원문에서 글자 그대로 복사. 한 글자도 바꾸지 않는다
- 종류 / 링크 / 마지막 확인(리서치 날짜와 동일) / 상태 = `후보`
- 출처 문서: 방금 만든 아카이브 페이지와 연결

## 4. 본문 쓰기 — 5블록 고정

이 순서와 개수를 바꾸지 않는다.

```
## 1. 용도
왜 이게 필요한지 2~3줄. 배경 설명 늘어놓지 않는다.

## 2. 바로 실행
복붙 가능한 코드블록. 설명은 코드 한 줄당 한 줄 이하.

## 3. 선택 기준
선택지가 여러 개일 때 "언제 뭘 쓰나". 표로.
선택지가 하나뿐이면 이 블록은 통째로 뺀다.

## 4. 함정
한계, 주의사항, 오탐 사례, 하면 안 되는 것.

## 5. ▶ 원문 전체
노션 토글 블록. 원문을 한 글자도 빼지 말고 그대로 넣는다.
```

## 5. 압축 규칙

줄이는 것
- 1~4번 블록 합쳐서 원문의 25% 이내
- 중복 설명, 수식어, "~할 수 있다" 류 완곡 표현
- 배경·역사 서술 (원문 토글에 남아 있으니 괜찮다)

절대 안 건드리는 것 (verbatim)
- 설치 명령어, 코드 블록, 파일 경로
- 버전 번호, 날짜, 스타 수, 수치
- URL
- 논문·저자·출처 이름

수치를 요약하다가 틀리느니 아예 빼는 게 낫다. 확실하지 않으면 원문 토글에만 남긴다.

## 6. 보고

끝나면 아래만 출력한다. 장황하게 설명하지 않는다.

```
✅ [페이지 제목]
   리서치 날짜: YYYY-MM-DD (부패속도: X) → 신선도 🟢/🟡/🔴
   도구 N개 등록: A, B, C
   ⚠️ 판단 애매했던 것: (있으면)
```

마지막 줄이 중요하다. 날짜를 추정했거나, 도구인지 아닌지 애매했거나, 원문이 스스로 모순되는 부분이 있었으면 반드시 여기에 적는다. 조용히 넘어가지 않는다.

## 7. 문체

정리한 본문은 한국어로 쓴다. 번역투를 쓰지 않는다.

- "~를 통해 / ~에 대해 / ~에 있어서" 안 씀
- 이중 피동("되어진다") 안 씀
- "결론적으로", "주목할 만하다", "시사하는 바가 크다" 안 씀
- 형식명사("것", "점", "수", "바") 남발 안 함
- 문장 길이에 변화를 준다
````
